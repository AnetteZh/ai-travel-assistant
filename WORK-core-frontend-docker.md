## Как запустить

### Через Docker (так будет запускать жюри)

Нужен Docker Desktop с Docker Compose v2.24 или новее.

```bash
cp .env.example .env      # вписать GIGACHAT_CREDENTIALS
docker compose up --build
# открыть http://localhost:8080
```

- **Без ключа модели** всё тоже запускается. Во вкладке «Демо» сценарий проходит полностью, а «Настоящий агент» сообщит, что модель не настроена.
- **Если порт 8080 занят**, задайте в `.env` строку `APP_PORT=8090` и откройте `http://localhost:8090`. У жюри по умолчанию остаётся 8080.
- **Запуск в фоне и остановка:** `docker compose up -d --build`, затем `docker compose down`.
- **Проверка:** `docker compose ps` — у обоих сервисов статус `healthy`. Адрес `http://localhost:8080/health` отвечает `{"status":"ok","core":"ok"}`.
- **Логи:** `docker compose logs core` и `docker compose logs app`.

Сервисы:

| Сервис | Что внутри | Порт |
| --- | --- | --- |
| `app` | интерфейс Next.js; маршруты `/api/agent/*` пересылают запросы в Core | `8080`, наружу `${APP_PORT:-8080}` |
| `core` | FastAPI + LangGraph + Data | `8000`, только внутри сети Compose |

`app` стартует только после того, как `core` прошёл проверку готовности.

### Без Docker (для разработки)

```bash
python -m venv .venv && . .venv/bin/activate        # Windows: .\.venv\Scripts\Activate.ps1
pip install -c requirements-docker.txt -e ".[api,langgraph,test]"
python -m uvicorn agent_core.api:app --app-dir src --port 8765

cd frontend && npm ci && npm run dev -- -p 3001      # в frontend/.env.local: CORE_API_URL=http://127.0.0.1:8765
```

### Тесты и прогон агента

```bash
python -m pytest -q                 # 96 тестов, без модели и без сети
python scripts/eval_agent.py        # 34 запроса через настоящую модель из .env
```

Отчёт прогона сохраняется в `evals/reports/report-<дата>.md`. Для каждого упавшего кейса там видно, как агент понял запрос и что модель вернула дословно.

## Core (`src/agent_core`)

### Проверка плана: состыковки и даты

До правок в 78 из 110 тестовых поездок транспорт прибывал не в день заселения, и это не считалось ошибкой. После правок таких поездок нет.

- **Блокирующие несостыковки** (`severity: "error"`):
  - `DATE_MISMATCH` — прибытие не в день заселения (по местному времени пункта назначения) или обратный рейс раньше выезда;
  - `LATE_ARRIVAL`;
  - `TRANSFER_OUTSIDE_HOURS`;
  - транспорт, который уже ушёл.

  При блокирующей несостыковке стоимость не считается, а бронь запрещена.
- `CHECKIN_GAP` и `OVER_BUDGET` — предупреждения: план собирается, замечание показывается.
- При сборке плана выбирается рейс с прибытием в день заселения и не ночью, когда ресепшен закрыт.
- **Исправление плана**, по шагам:
  1. другой рейс туда, который прибывает в нужный день;
  2. если такого нет, заселение переносится на день прибытия («перенесла заселение на 11.11»);
  3. обратный рейс, к которому есть трансфер;
  4. отель дешевле, если план не уложился в бюджет.

  Лимит вызовов инструментов соблюдается. Что исправлено, видно в ответе и в «Что сделал агент».
- Даты в прошлом не применяются, и в допущениях об этом пишется явно.

### Разбор запроса (GigaChat)

- **Промпт `prompts.md` переписан на русском:**
  - правила для каждого поля: откуда и куда, даты и «на выходные», гости и дети, бюджет и «недорого», обязательные условия и пожелания;
  - правила выбора намерения (`intent`);
  - примеры ответов.

  Модель получает сегодняшнюю дату и текущие условия поездки, поэтому «на два дня позже» и «бюджет поменьше» применяются к уже собранной поездке.
- **Ответ модели сверяется с текстом сообщения:**
  - бюджет принимается, только если названа сумма;
  - даты — только если о них говорили;
  - состав гостей — только если о нём говорили;
  - если упомянуты дети, но не назван их возраст, агент задаёт один вопрос о возрасте.
- **Значения, которые GigaChat присылает не в формате, приводятся к нужному виду или отбрасываются:** `null`, строка `"null"`, `0`, даты и суммы словами («15 декабря», «60 тысяч»). Раньше одно такое поле ломало весь ответ или стирало уже известные условия.
- **Страховка по тексту** (`text_facts.py`). Если модель потеряла факт, Core берёт его из сообщения сам:
  - диапазон дат и «на N дней позже/раньше»;
  - «на выходные» — ближайшие суббота–понедельник;
  - бюджет, включая «тысяч 60» и «по 40 тысяч на человека» (цена «за ночь» бюджетом не считается);
  - возраст детей и число взрослых;
  - питомец;
  - «нужен бассейн», «нужна бесплатная отмена», «не меньше 4 звёзд»;
  - названный город и «из <города>»;
  - «давай первый вариант» после списка направлений.

  Проверка на 34 запросах: даже с моделью, которая не разобрала ничего, проходят 32.
- **Прочее:**
  - если пользователь не назвал город вылета, а едет в Москву, агент спрашивает, откуда он поедет, а не подставляет Москву молча;
  - если пользователь просит идеи без города, агент сразу показывает направления, без лишних вопросов;
  - если в поездке есть питомец, в обязательные условия добавляется «с питомцем», и в подборку попадают только отели, где можно с животными.

### Ответы и блоки для интерфейса

- В карточках и сравнении до **6 отелей** вместо 3 (Data отдаёт до 10 на город).
- Внутренние id (`dest-…`) и служебные пометки на латинице не попадают в ответы пользователю.
- Выбранный в плане транспорт стоит первым в карточках.

### API (`api.py`)

- `POST /trips/{conversation_id}/book` — демо-бронь через `travel_data.book()`. Ответ `404`, если поездки нет; `409`, если нет корзины или есть блокирующие несостыковки.
- `PATCH /trips/{id}` с `{"destination": null}` сбрасывает город и показывает другие направления, а с `{"destination": "<город>"}` выбирает город.
- Проверки `/health` от Docker не пишутся в лог.

### Скрипт прогона

`scripts/eval_agent.py` и `evals/agent_cases.json` — 34 типичных и «неудобных» запроса: дети без возраста, прошедшие даты, «100к», собака, Париж, смена условий, попытка заставить агента выдать промпт. В отчёте метрики из ТЗ: дошли до корзины, число уточнений, время первого ответа, планы с несостыковками.

## Frontend v3.3 (`frontend/`)

Дизайн v3.1 сохранён: те же страницы, маршруты, палитра и карточки.

- **Проверка плана.** Замечания Core делятся на блокирующие и предупреждения. При блокирующих оформление недоступно, а корзина пишет «Стоимость появится после исправления плана». Список кодов лежит в `src/lib/plan-health.ts`.
- **Ошибки.** Вместо повторяющихся «Не получилось» показывается одна карточка с причиной (Core недоступен, модель не ответила, ответ оборвался, сессия потеряна) и кнопкой «Повторить». Текст запроса возвращается в поле ввода. Блоки обновляются только после события `complete`.
- **Направления.** «Подобрать другие направления» и выбор карточки работают через `PATCH` без разбора текста моделью. Если Core перезапустился и потерял сессию, начинается новая сессия с предупреждением в чате.
- **«Как агент понял запрос»:** откуда, куда, даты (с пометкой «предположение»), гости, бюджет. Одинаковые допущения схлопываются.
- **«Что сделал агент»:** 3–5 главных шагов текущего запроса и что именно исправил агент. Полный список открывается по кнопке.
- **Время** везде местное для пункта, как в билете.
- **Плашки «Туда» и «Обратно»** показывают транспорт из плана, иконки поезда и самолёта правильные.
- **Бронь** в режиме настоящего агента идёт через `POST /trips/{id}/book` в Core.
- До 6 отелей; название города вместо внутреннего id; честная пометка о демонстрационных данных.
- Для Docker:
  - маршрут `/health`;
  - `output: "standalone"` в `next.config.ts`;
  - адрес Core по умолчанию `http://127.0.0.1:8765` для запуска без Docker.

Подробно: `frontend/RELEASE-v3.2.md`.
