# Техническое задание для Core AI — агент путешествий «Островок»

> **Назначение файла:** инструкция для coding agent в VS Code. Реализуй только модуль **Core AI** — оркестрацию диалога и LangGraph-граф, который использует уже существующий `travel_data`. Не переписывай модуль Data и не создавай фронтенд.

## 1. Сначала изучи репозиторий

Перед изменениями прочитай:

1. `DATA_FILE_GUIDE.md` — описание существующего модуля Data и его контрактов.
2. `pyproject.toml`, `README.md`, `.env.example`.
3. Реальный код `src/travel_data/`, особенно `models.py`, `tools.py`, `world.py`, `langgraph_adapter.py`, `__init__.py`.
4. Существующие тесты, примеры и скрипты.

**Важно:** `DATA_FILE_GUIDE.md` — карта модуля генерации модуля data проекта, а не замена исходному коду. Сверяй названия функций, поля моделей и сигнатуры с реальной реализацией. Не предполагай, что функция существует, только потому что она названа в этом ТЗ.

До реализации кратко зафиксируй для себя:
- какие Data-модели и инструменты доступны сейчас;
- какие контракты Core нужно добавить;
- как безопасно преобразовать Core-запрос в аргументы существующих Data-инструментов.

## 2. Границы задачи

### Входит в Core AI

- разбор пользовательского сообщения в структурированный запрос поездки;
- поддержка допущений вместо длинной анкеты;
- явное состояние поездки `TripState`;
- граф LangGraph и выбор следующего действия;
- вызов существующих инструментов `travel_data`;
- сборка и проверка плана, ограниченная автоматическая попытка исправить конфликты;
- пересборка после изменения условий с версионированием и `plan_diff`;
- объяснения на основе результатов инструментов и `Evidence`;
- формирование JSON-совместимых UI-блоков;
- FastAPI-эндпоинты и поток статусов/блоков через SSE;
- обработка ошибок модели, сети и инструментов;
- тесты Core и интеграционные тесты с Data.

### Не входит в Core

- переписывание `travel_data`, генератора мира, `world.json` и его копий;
- изменение алгоритмов Data-поиска, ранжирования, расчёта цены и погоды без согласования с владельцем Data;
- разработка React/Next.js-интерфейса;
- полноценный модуль оценки качества, эталон разметки и симулятор пользователей;
- SQLite-профиль пользователя и сценарии после покупки — это дополнительные задачи, выполнять только после основного сквозного сценария;
- настоящая оплата или реальные бронирования. `travel_data.book()` создаёт только демонстрационную бронь.

Не меняй чужие файлы и публичные контракты без необходимости. Если Data не предоставляет требуемую функцию, сначала создай тонкий адаптер на стороне Core или оставь явно описанный интерфейс интеграции; не переписывай Data-модуль молча.

## 3. Что уже реализовано в Data

По `DATA_FILE_GUIDE.md`, пакет `src/travel_data/` содержит:

- `models.py` — Pydantic-модели данных, включая `TravelBrief`, `TravelRequest`, `HotelRecord`, `Evidence`, `WeatherSummary`, `Cart`, `BookingResult`;
- `world.py` — загрузку и валидацию мок-мира из `world.json`;
- `tools.py` — инструменты поиска и расчёта;
- `codes.py` — словарь причин и рисков;
- `langgraph_adapter.py` — адаптер функций Data в инструменты LangChain;
- `__init__.py` — публичные экспорты пакета.

Согласно путеводителю, Data-инструменты включают:

- `suggest_destinations()` — варианты направлений;
- `search_hotels()` — фильтрация и ранжирование отелей;
- `search_transport()` — варианты перелётов/поездов;
- `search_transfers()` — трансферы;
- `price_cart()` — программный расчёт стоимости;
- `book()` — только демонстрационная бронь;
- `get_weather()` — погода: MET Norway, затем Open-Meteo, затем явно помеченная синтетическая оценка.

Мок-мир синтетический. Нельзя выдавать его за каталог реальных предложений. Погоду и любые другие синтетические данные нужно явно маркировать.

**Обязательно проверь код:** наличие `check_plan`, фактические сигнатуры и форматы результатов могут отличаться от описания выше. Не изменяй Data только ради того, чтобы он совпал с предположениями агента.

## 4. Технологии и общие правила

- Python `>=3.11`.
- Pydantic v2 для контрактов и валидации.
- LangGraph для графа агента. Не заменяй его самописным циклом `while`.
- `langchain-openai` для вызова OpenAI-моделей через LangChain.
- FastAPI для HTTP API.
- SSE для отправки промежуточных статусов и итоговых блоков.
- `httpx` и существующие Data-инструменты для сетевых запросов; не дублируй погодную интеграцию.
- Конфигурация через переменные окружения и `.env`; секреты не коммитить.
- Все границы между модулями должны быть типизированы. Для новых контрактов используй строгую валидацию Pydantic v2 (`extra="forbid"`, неизменяемость там, где она не мешает управляемым обновлениям состояния).
- Внешние ответы и вывод LLM считать недоверенными: проверять их до использования.
- Не выдумывать цены, длительности, удобства, расписания и факты об отелях.

## 6. Контракт состояния поездки

`TripState` — единственный источник актуального состояния поездки. Не храни существенные требования только в истории чата или в свободном тексте.

Реализуй Pydantic-контракты как минимум для следующих сущностей. Используй точные типы и разумные значения по умолчанию; не добавляй поля, которые не нужны основному сценарию.

### `TripRequest`

Данные, которые хочет пользователь:

- `origin: str | None` — город отправления;
- `destination: str | None` — если `None`, пользователь пока выбирает направление;
- `date_from: date | None`;
- `date_to: date | None`;
- `flexible_days: int = 0`;
- `guests` — взрослые, возраст детей, питомцы;
- `budget_total: int | None` — общий бюджет поездки в рублях;
- `hard` — жёсткие ограничения, которые должны фильтровать варианты;
- `soft` — пожелания, влияющие на ранжирование;
- `mood: str | None` — например, «релакс» или «активно»;
- `weights` — приоритеты цены, времени в пути, отмены и локации.

Учитывай различие:
- **hard constraints** нельзя компенсировать высоким рейтингом;
- **soft preferences** влияют на оценку и порядок вариантов.

Не добавляй в запрос ограничения, которых пользователь не называл. Если часть данных выведена предположением, сохраняй её также в `assumptions`.

### `TripState`

Как минимум:

- `request: TripRequest`;
- `assumptions` — явные допущения агента;
- `destinations`, `hotels`, `transport`, `transfers` — результаты поиска или `None`;
- `plan` — выбранная связка компонентов поездки или `None`;
- `cart` — рассчитанная корзина или `None`;
- `issues` — конфликты и риски;
- `stage` — текущая стадия сценария;
- `version: int` — увеличивается при каждой успешной пересборке плана.

При обновлении запроса не теряй уже известные значения без причины. Внутренние изменения состояния должны быть явными и валидироваться. Предыдущую версию состояния/плана сохраняй настолько просто, насколько нужно для возврата и сравнения.

### Контракты и факты

- Новые модели контрактов должны запрещать неожиданные поля (`extra="forbid"`).
- Каждое фактическое утверждение о варианте поездки должно быть связано с `Evidence`: идентификатором, источником, путём к полю и `is_synthetic`.
- Различай `FACT`, `ASSUMPTION`, `AI_INFERENCE` и `RISK`.
- Если утверждение не подтверждается данными, не показывай его как факт.
- Не дублируй без необходимости модели `travel_data`. Если Data-модель уже подходит, используй её; если контракт Core отличается, преобразуй данные явным адаптером и не меняй Data-модель без согласования.

## 7. LangGraph: поведение агента

Собери граф с понятными узлами и условными переходами. Названия можно адаптировать к реализации, но логика должна оставаться явной:

1. **Parse request** — извлечь из нового сообщения поля `TripRequest` с помощью структурированного вывода модели.
2. **Merge request** — применить распознанные изменения к текущему `TripState`, не сбрасывая неупомянутые условия.
3. **Resolve assumptions** — предложить разумные допущения и записать их в состояние. Показывать их пользователю так, чтобы он мог поправить их.
4. **Choose action** — выбрать следующее действие на основе состояния и цели пользователя.
5. **Search** — вызвать необходимые Data-инструменты.
6. **Build plan** — собрать согласованный вариант из выбранного направления, отеля, транспорта и трансфера.
7. **Check plan** — проверить даты, время, бюджет и ограничения программно.
8. **Repair plan** — при конфликте ограниченно попробовать альтернативу (например, другой рейс или трансфер); не зацикливаться.
9. **Explain** — сформировать объяснение только по проверенным результатам, причинам, рискам и `Evidence`.
10. **Build response** — вернуть список UI-блоков и актуальное состояние.

Узлы должны быть отдельными функциями, а маршрутизация — задаваться условными переходами LangGraph. Не реализуй бесконтрольный автономный цикл.

### Правила выбора действия

- Если направление не задано и пользователь просит идеи — используй `suggest_destinations`.
- Если направление известно — ищи подходящие отели и транспорт в соответствии с имеющимися условиями.
- Если есть выбранные компоненты — собери план, найди трансфер, если он нужен, посчитай стоимость и проверь состыковки.
- Если пользователь меняет условия, распознай это как патч к текущему `TripRequest`, а не как полностью новый запрос.
- Если обязательных данных не хватает и предположение сделает план заведомо неверным (например, возраст ребёнка критичен для размещения), задай **не больше одного уточняющего вопроса за ход**.
- В остальных случаях предпочитай явное разумное допущение вместо длинной анкеты.
- Ограничь вызовы каждого поискового инструмента максимум тремя за один ход агента.
- Перед формированием корзины обязательно выполняй программную проверку плана. Проверка второй моделью, если она будет реализована, запускается только перед корзиной, а не на каждом сообщении.

## 8. Проверка плана и автоматическое исправление

Проверяй кодом, а не просьбой к LLM «подумать»:

- даты проживания совпадают с датами поездки;
- прибытие, трансфер, заселение, выезд и обратный транспорт состыкованы с учётом часовых поясов;
- время прибытия не конфликтует с часами работы ресепшена/трансфера;
- пересадка не короче допустимого порога, если эти данные доступны;
- жёсткие ограничения соблюдены;
- итоговая сумма рассчитана инструментом Data и сопоставлена с бюджетом;
- превышение бюджета всегда отображается как риск;
- отсутствующие ссылки на объекты или недопустимые значения не проходят в ответ.

В ТЗ используются коды причин и рисков: `MATCHES_HARD`, `KID_FRIENDLY`, `FREE_CANCELLATION`, `SHORT_TRAVEL`, `NEAR_POI`, `OVER_BUDGET`, `LATE_ARRIVAL`, `CHECKIN_GAP`, `TIGHT_CONNECTION`, `NON_REFUNDABLE`, `WEATHER_RISK`, `DATE_MISMATCH`, а также `UNSUPPORTED_NUMBER` для неподтверждённых чисел. Если код уже реализован в Data, используй его. Не создавай второй конфликтующий словарь. Если какого-то кода или проверочного инструмента нет, зафиксируй это и реализуй только ту проверку, для которой есть достаточные поля; не имитируй неизвестные данные.

При конфликте агент может сделать ограниченную попытку подобрать замену. После одной попытки исправления:
- повторно проверь план;
- если конфликт остался, покажи его честно;
- не выдавай заведомо некорректный план за безопасный;
- запиши действия и ошибки в trace.

## 9. Пересборка и `plan_diff`

Изменение запроса — патч, а не новый диалог с нуля. Добавь минимальную карту зависимостей:

| Изменение | Что пересчитать | Что можно сохранить |
|---|---|---|
| Даты | транспорт, доступность/цены отеля, трансфер, погоду, итог | направление и пожелания |
| Бюджет | фильтрацию/ранжирование и при необходимости отель | направление и транспорт, если они подходят |
| Гости или питомцы | отели, размещение, цены, соответствие ограничений | направление и даты |
| Направление | поиск зависимых компонентов поездки | общие требования и веса |
| Веса | только ранжирование имеющихся вариантов | результаты поиска |

После пересборки:
- увеличь `TripState.version`;
- сформируй `plan_diff`: что осталось прежним, что заменено и как изменился итог;
- сохрани предыдущую версию, если это не требует тяжёлой инфраструктуры;
- не пересчитывай независимые компоненты без необходимости.

## 10. Объяснения и UI-блоки

Агент возвращает список структурированных блоков, а не один большой свободный текст. Контракт каждого блока должен быть JSON-сериализуемым и пригодным для фронтенда.

Поддержи минимально следующие типы:

- `message` — короткий текст агента;
- `assumptions` — список допущений, которые можно исправить;
- `destination_cards` — до 3 подходящих направлений, с ценой, погодой, временем в пути и причинами, если эти данные доступны;
- `option_cards` — отели/транспорт с причинами и рисками;
- `comparison` — сравнение по пользовательским весам;
- `trip_timeline` — последовательность вылета, прибытия, трансфера и заселения, когда данные доступны;
- `plan_diff` — изменения после пересборки;
- `cart` — позиции, программный итог и статус проверок;
- `trace` — этапы обработки и вызовы инструментов для демонстрации.

Не нужно обязательно выводить все блоки на каждом ходе: возвращай только те, для которых есть данные. Не придумывай пустые карточки для заполнения ответа.

Текст объяснений должен:
- опираться на причины и риски, возвращённые кодом;
- связывать фактические утверждения с `Evidence`;
- явно отмечать синтетические данные и допущения;
- не показывать внутренние ID (`H-0142`, `EV-...`) и имена полей пользователю;
- не содержать чисел о цене, времени или удобствах, не подтверждённых данными;
- прямо говорить, если подходящего варианта нет, и показывать ближайшие альтернативы с указанием нарушенного ограничения.

## 11. FastAPI и SSE

Реализуй минимальный API для проверки основного сценария. Точные пути можно выбрать с учётом текущего проекта, но документируй их в README.

Нужны:
- эндпоинт для отправки пользовательского сообщения и получения результата;
- эндпоинт для патча `TripRequest` (например, исправление допущения или изменение веса);
- health-check.

Для основного диалога используй SSE: сначала отправляй статусы выполнения («разбираю запрос», «ищу направления», «проверяю план»), затем готовые UI-блоки и финальное событие. Формат событий должен быть стабилен и описан в README.

Не обещай потоковый вывод токенов, если реализован только поток событий/статусов. Ошибка модели или Data-инструмента должна превращаться в понятное событие ошибки и не приводить к необработанному падению сервера.

Если состояние между HTTP-запросами необходимо для демонстрации, используй предусмотренный LangGraph checkpointer или простой локальный механизм только после проверки требований проекта. Не добавляй внешнюю базу данных без необходимости. Не допускай, чтобы разные пользователи случайно изменяли один и тот же `TripState`.

## 12. Конфигурация модели и ошибки

- Используй `ChatOpenAI` и Structured Outputs для разбора запроса.
- Имя модели, таймауты и лимиты задавай через конфигурацию/переменные окружения.
- `OPENAI_API_KEY` читается из окружения или локального `.env`; ключ нельзя хардкодить, логировать или коммитить.
- При сетевой ошибке допускай ограниченный повтор; после исчерпания попыток верни понятную ошибку.
- Если модель вернула пустой/невалидный результат, выполни не более одной повторной попытки или запроси уточнение.
- Ограничь число действий инструментов на ход и число автоматических исправлений.
- В `trace` фиксируй стадию, инструмент, результат/ошибку и причину перехода, но не записывай секреты и полные чувствительные данные пользователя.

## 13. Минимальные сценарии приёмки

Добавь тесты Core. По возможности используй подменённую модель и фикстуры, чтобы тесты не требовали настоящего OpenAI API или доступа к сети.

1. **Запрос без направления:** агент выдаёт направления, а не падает из-за `destination=None`.
2. **Запрос с направлением:** агент использует Data для поиска вариантов отеля и транспорта.
3. **Неполный запрос:** агент делает явные допущения и задаёт максимум один необходимый вопрос за ход.
4. **Патч условий:** изменение бюджета/дат/гостей сохраняет остальные поля `TripRequest`.
5. **Проверка плана:** конфликт вызывает ограниченную попытку исправления; нерешённый риск остаётся видимым.
6. **Корзина:** итог приходит из программного расчёта Data, не вычисляется LLM.
7. **Evidence:** неподтверждённый факт или число не попадает в финальные UI-блоки как достоверное утверждение.
8. **Синтетические данные:** в ответе/источниках явно помечено `is_synthetic`.
9. **Пересборка:** `version` растёт, `plan_diff` показывает изменения, независимые части сохраняются.
10. **SSE/API:** успешный запрос выдаёт последовательность событий статуса и блоков; ошибка модели/инструмента возвращается в контролируемом формате.
11. **Лимиты:** за один ход каждый поисковый инструмент вызывается не более трёх раз.
12. **Регрессия Data:** существующие тесты Data и команды генерации/валидации остаются работоспособными.

Тесты должны проверять поведение и контракты, а не внутренние детали реализации. Не вызывай настоящую оплату, реальные бронирования или OpenAI API в обычном тестовом прогоне.

## 14. Порядок реализации

Работай короткими проверяемыми этапами:

1. **Аудит:** изучи код Data и зафиксируй реальные сигнатуры/модели.
2. **Контракты:** создай/согласуй `TripRequest`, `TripState`, `Evidence`, `Issue`, UI-блоки и явные адаптеры.
3. **Вертикальный MVP:** один сценарий «сообщение → направления → отель/транспорт → корзина → проверка».
4. **LangGraph:** добавь узлы, условные переходы, trace и лимиты.
5. **Пересборка:** патчи, карта зависимостей, версия состояния и `plan_diff`.
6. **API/SSE:** подключи Core к FastAPI.
7. **Проверки:** тесты с фикстурами, затем весь существующий набор тестов и проверка мира.
8. **Документация:** дополни README запуском API, переменными окружения и примерами запросов.

После каждого этапа запускай подходящие тесты. Не маскируй ошибки, не удаляй существующие тесты и не переписывай Data ради быстрого прохождения.

## 15. Критерии готовности

Core считается готовым для базовой демонстрации, когда:

- пользователь может отправить обычное сообщение о поездке;
- состояние хранится в типизированном `TripState`;
- граф LangGraph выбирает и выполняет следующий шаг;
- данные приходят из существующего `travel_data`;
- агент возвращает UI-блоки с допущениями, причинами, рисками и источниками там, где это применимо;
- цена рассчитывается кодом, план проверяется кодом;
- конфликт либо исправляется ограниченной попыткой, либо честно показывается;
- изменения условий запускают частичную пересборку с `plan_diff` и новой версией;
- FastAPI работает, SSE отдаёт статусы и блоки;
- новые тесты проходят, существующие тесты Data не сломаны;
- моковые данные не выдаются за реальные предложения.

**Если требования исходного ТЗ конфликтуют с реально существующим Data-контрактом, не угадывай.** Сохрани Data-модуль, добавь явный адаптер на стороне Core и перечисли оставшиеся несовпадения в итоговом отчёте. В конце работы сообщи, какие файлы созданы/изменены, какие тесты запущены и что осталось за пределами Core.
