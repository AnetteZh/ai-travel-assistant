# «О!дин запрос» — AI-агент путешествий

## О проекте

«О!дин запрос» — прототип AI-агента для планирования путешествий, разрабатываемый для хакатона Островка. Пользователь описывает поездку обычным языком, а агент помогает подобрать направление, транспорт, отель и трансфер, учитывает бюджет и предпочтения, проверяет совместимость вариантов и формирует согласованный план путешествия.

Цель проекта — позволить пользователю решать основные задачи планирования в одном диалоге, без необходимости вручную искать и сопоставлять предложения из разных источников.

Проект пока что разделён на два основных модуля:

- **Core AI** — диалоговая логика, интерпретация запросов, управление состоянием поездки, оркестрация инструментов, проверка плана и формирование ответа пользователю.
- **Travel Data** — данные о направлениях и вариантах поездки, поиск, фильтрация, ранжирование, получение погоды и детерминированный расчёт стоимости.

Core использует Travel Data как набор инструментов. Data не управляет диалогом и не реализует собственный цикл агента.

На текущем этапе Travel Data работает с синтетическим миром. Его результаты предназначены для демонстрации и не должны представляться пользователю как реальные предложения поставщиков.

## Архитектура и разделение ответственности

### Core AI — агентская логика

Core отвечает за взаимодействие с пользователем и управление сценарием планирования поездки. Для реализации агентской логики используется LangGraph.

Основные задачи Core:

- преобразование сообщения пользователя в структурированный запрос поездки;
- сохранение требований, предпочтений и допущений в общем состоянии `TripState`;
- выбор следующего действия и вызов инструментов Travel Data;
- сборка согласованного плана из направления, транспорта, отеля и трансфера;
- проверка дат, бюджета, ограничений и временных стыковок;
- ограниченная попытка исправить обнаруженные конфликты;
- частичная пересборка плана при изменении условий с сохранением независимых результатов;
- объяснение рекомендаций на основе причин, рисков и подтверждающих данных;
- формирование структурированных UI-блоков;
- предоставление API для клиентского интерфейса.

Core не должен самостоятельно выдумывать цены, расписания или характеристики объектов. Расчёты и проверки, для которых доступны детерминированные инструменты, выполняются программно.

### Travel Data — данные и инструменты

Travel Data предоставляет функции, которые Core вызывает на соответствующих этапах сценария.

Модуль отвечает за:

- загрузку и проверку синтетического мира;
- подбор направлений;
- поиск и ранжирование отелей;
- поиск транспорта и трансферов;
- получение погодной информации;
- расчёт стоимости выбранных компонентов;
- демонстрационную имитацию бронирования;
- предоставление причин рекомендаций, рисков и `Evidence`.

**Текущее состояние:** модуль Travel Data уже реализован. Его фактические модели, функции и контракты описаны далее. Core должен интегрироваться с существующей реализацией, а не создавать параллельные версии тех же инструментов.

## Технологии

- Python 3.11+
- LangGraph — оркестрация агентского сценария
- LangChain и `langchain-openai` — взаимодействие с LLM и структурированный вывод
- Pydantic v2 — типизированные модели и валидация
- FastAPI — HTTP API

## Travel Data: реализованный модуль

Travel Data — отдельный Python-пакет `travel_data`. Он не зависит от собственного цикла LLM-агента и может использоваться как обычная библиотека или подключаться к LangGraph через адаптер инструментов.

### Состав синтетического мира

| Данные | Объём и содержание |
|---|---|
| Направления | 20 направлений России с координатами, аэропортами, вокзалами, часовыми поясами, тегами и синтетическими климатическими данными |
| Отели | 200 моковых отелей — по 10 на направление |
| Транспорт | 760 шаблонов железнодорожных и авиамаршрутов между направлениями |
| Трансферы | 120 шаблонов такси, шаттлов и автобусов от аэропортов и вокзалов |

Отели содержат данные о цене за ночь, звёздах, рейтинге, бассейне, размещении с питомцами, спа, питании, отмене, семейных удобствах, времени заселения и работы ресепшена, расстояниях до центра или пляжа и координатах.

Шаблоны транспорта преобразуются в конкретные варианты с датами и временными метками с учётом часовых поясов при поиске.

Мок-мир генерируется детерминированно, без LLM и API-ключей. Названия и описания отелей создаются скриптом `scripts/generate_world.py`. Это позволяет воспроизводить результаты и запускать модуль независимо от LLM.

### Инструменты Travel Data

| Инструмент | Назначение |
|---|---|
| `suggest_destinations` | Подбор направлений с ориентиром стоимости, погодой, причинами и Evidence |
| `search_hotels` | Поиск и ранжирование отелей с учётом ограничений и предпочтений |
| `search_transport` | Подбор транспорта туда и обратно с временем и длительностью |
| `search_transfers` | Подбор трансферов между терминалом и отелем с проверкой времени |
| `price_cart` | Детерминированный расчёт общей стоимости выбранных компонентов |
| `book` | Создание демонстрационной брони без реального платежа |
| `get_weather` | Получение погодной информации с последовательным использованием доступных источников |

При ранжировании мягкие предпочтения влияют на оценку вариантов, а жёсткие требования используются для фильтрации. Результаты могут содержать `pros`, `cons`, `why_it_fits`, `reason_codes`, `risk_codes` и `Evidence`.

Синтетические отели, маршруты, трансферы и связанные доказательства помечаются `is_synthetic=true`. Источник погодных данных также указывается в результате; синтетическая климатическая оценка явно обозначается как fallback.

### Контракты и интеграция с Core

Основные модели расположены в `src/travel_data/models.py`. Среди них:

- `TravelBrief` — базовые требования к поездке;
- `TravelRequest` — запрос с датами, направлением, бюджетом и весами;
- `Guests` — информация о путешественниках;
- `Evidence` — сведения об источнике подтверждения;
- `CartSelection` и `Cart` — выбор компонентов и рассчитанная корзина;
- `BookingResult` — результат демонстрационной брони.

Фактические определения и сигнатуры необходимо сверять с исходным кодом.

`TravelBrief` содержит согласуемые поля `guests`, `hard_requirements`, `soft_preferences` и `mood`. `TravelRequest` расширяет базовый запрос датами, направлением, бюджетом и весами.

Core должен преобразовывать своё состояние `TripRequest` в `TravelRequest` либо использовать согласованную общую модель. `hard_requirements` и `soft_preferences` представлены списками строк, поэтому соответствие структурированных требований пользователя значениям, поддерживаемым Data, необходимо явно определить на стороне интеграции.

При отсутствии дат Data использует временный период через 14 дней продолжительностью 7 ночей и возвращает это допущение в `assumptions`. Core должен показать его пользователю и позволить изменить.

Для подключения инструментов через LangChain доступен адаптер:

```python
from travel_data.langgraph_adapter import as_langgraph_tools

tools = as_langgraph_tools()
```

Полученный список можно использовать в графе LangGraph. При необходимости Core также может вызывать функции из `travel_data.tools` напрямую из собственных узлов.

При восстановлении состояния через checkpointer следует сохранять выбранные транспортные и трансферные объекты либо их достаточные данные, а не полагаться исключительно на локальные кэши ID.

### Стоимость и бронирование

`price_cart` рассчитывает стоимость программно по выбранным компонентам и возвращает риск `OVER_BUDGET` при превышении бюджета. LLM не должна самостоятельно рассчитывать итоговую стоимость.

`book` создаёт демонстрационный результат с номером вида `DEMO-...`. Реальные поставщики, платежи и бронирования не вызываются.

### Погода

`get_weather(destination_id, target_date)` использует источники в следующем порядке:

1. **MET Norway Locationforecast API** — основной источник для доступных прогнозов примерно на девять дней вперёд.
2. **Open-Meteo Forecast API** — резервный источник при недоступности первого провайдера или выходе даты за пределы его окна.
3. **Синтетическая месячная климатическая оценка** — последний fallback, помеченный `is_synthetic=true` и `source="synthetic monthly climate estimate"`.

Внешние клиенты используют `trust_env=False`, чтобы случайные proxy-переменные Windows не нарушали запросы. Ответы MET Norway кешируются в `~/.cache/travel_data/met_norway` с учётом `Expires` и `Last-Modified`.

Вероятность осадков не подменяется количеством осадков и может отсутствовать (`null`).

Документация провайдеров:
- [MET Norway Locationforecast](https://api.met.no/doc/locationforecast/HowTO)
- [Open-Meteo Forecast API](https://open-meteo.com/en/docs)

Настройки задаются переменными окружения:

- `MET_NO_ENABLED=true` — включение MET Norway;
- `MET_NO_TIMEOUT_SECONDS=5` — таймаут MET Norway;
- `MET_NO_USER_AGENT` — реальный контакт команды или публичный URL репозитория;
- `OPEN_METEO_ENABLED=true` — включение Open-Meteo;
- `OPEN_METEO_TIMEOUT_SECONDS=2.5` — таймаут Open-Meteo;
- `TRAVEL_DATA_WORLD_PATH` — альтернативный путь к `world.json`.

Перед публикацией демо необходимо проверить условия использования, кеширования и атрибуции обоих погодных источников.

## Что требуется для интеграции

При дальнейшей разработке Core необходимо:

1. Изучить реальные модели и сигнатуры `travel_data`, прежде чем вызывать инструменты.
2. Реализовать типизированное состояние поездки и граф LangGraph.
3. Преобразовывать пользовательские сообщения в обновления существующего запроса, сохраняя ранее указанные условия.
4. Использовать Data для поиска и расчёта стоимости, а не дублировать эти алгоритмы в Core.
5. Проверять план программно и явно показывать неподтверждённые допущения и риски.
6. Обеспечить API для клиентского интерфейса и поток статусов/результатов.
7. Запускать тесты Core вместе с существующими проверками Data.

На уровне общего приложения также потребуются согласованные Docker-конфигурация, FastAPI entrypoint, health-check на `/health`, порт `8080` и общий `.env.example`. Их следует объединить с Core/API-частью, не создавая параллельное приложение для Data.

## Core AI: запуск API

Агентский модуль находится в `src/agent_core/`. Он использует LangGraph для
диалога, существующие инструменты `travel_data` для поиска и расчёта, а промпты
хранятся отдельно в `src/agent_core/prompts.md`.

Установка зависимостей и запуск из корня проекта в PowerShell:

```powershell
pip install -e ".[api,langgraph,test]"
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
python -m uvicorn agent_core.api:app --app-dir src --host 127.0.0.1 --port 8080
```

Провайдер выбирается через `LLM_PROVIDER`:

- `openai_compatible` — production-подключение через `ChatOpenAI`. Задайте
  `OPENAI_API_KEY`, `OPENAI_MODEL`, а для совместимого стороннего API при
  необходимости — `OPENAI_COMPATIBLE_BASE_URL`. Если URL пустой, используется
  стандартный OpenAI endpoint.
- `gigachat` — тестовое подключение через `langchain-gigachat`. Задайте
  `GIGACHAT_CREDENTIALS`, при необходимости `GIGACHAT_MODEL` и
  `GIGACHAT_SCOPE` (по умолчанию `GIGACHAT_API_PERS`).

Оба провайдера используют один и тот же Pydantic structured output для разбора
запроса; провайдер и секреты задаются в локальном `.env`, не в коде. Файл
`.env.example` содержит только заглушки. Таймаут обоих подключений задаётся
через `OPENAI_TIMEOUT_SECONDS`.
Лимиты поисков и автоматического исправления: `AGENT_MAX_SEARCH_CALLS` (не более
3) и `AGENT_MAX_REPAIRS` (не более 1). Без действующего ключа endpoint вернёт
контролируемое SSE-событие ошибки.

### HTTP и SSE

- `GET /health` — проверка доступности.
- `POST /chat` — тело `{"message":"Хочу в Сочи на неделю","conversation_id":null}`.
  Ответ — SSE-события `status`, `block`, затем `complete`. `complete` содержит
  `conversation_id` и актуальный JSON `TripState`; поток токенов модели не
  реализован.
- `PATCH /trips/{conversation_id}` — тело `{"patch":{"budget_total":80000}}`;
  изменяет только переданные поля и возвращает состояние с UI-блоками.
  `{"patch":{"destination":null}}` сбрасывает направление и запускает новый подбор
  направлений с сохранением остальных условий; `{"patch":{"destination":"Казань"}}`
  выбирает направление без разбора текста моделью.
- `POST /trips/{conversation_id}/book` — демонстрационная бронь рассчитанной корзины
  через `travel_data.book()`. Ответ: `booking_id`, `status`, `message`, `booked_at`, `cart`.
  `404` — поездка не найдена (например, после перезапуска сервера); `409` — корзина не
  рассчитана или в плане есть блокирующие несостыковки. Реальной оплаты нет.

Замечания плана (`issues`) имеют `severity`. `error` — план не работает
(`DATE_MISMATCH`, `LATE_ARRIVAL`, `TRANSFER_OUTSIDE_HOURS`): корзина не считается, бронь
недоступна. `warning` — риск, который нужно показать (`CHECKIN_GAP`, `OVER_BUDGET`).
Перед показом агент делает одну попытку исправить конфликт: другой транспорт туда или
обратно из уже найденных, сдвиг заселения на день прибытия, более дешёвый отель.

Состояния живут в памяти процесса и теряются при перезапуске. Для нескольких
процессов или production нужна отдельная авторизованная система хранения.
Нынешний API предназначен для локальной демонстрации; не публикуйте его без
аутентификации.

### Прогон агента по набору запросов

`evals/agent_cases.json` — 34 типичных и «неудобных» запроса с ожиданиями: что агент должен
понять (город вылета, направление, даты, гости, бюджет, обязательные условия), какие блоки
показать и когда задать уточняющий вопрос. Прогон идёт через настоящую модель из `.env`:

```powershell
.\.venv\Scripts\python.exe scripts\eval_agent.py
.\.venv\Scripts\python.exe scripts\eval_agent.py --only sochi-basic,pets
```

Отчёт с расхождениями и метриками (дошли до корзины, число уточнений, время первого ответа,
планы с блокирующими несостыковками) сохраняется в `evals/reports/` в Markdown и JSON.
Ключи модели в отчёт не попадают. Новый неудобный запрос — новый объект в `agent_cases.json`.

### Проверка Core из терминала

Для ручной проверки алгоритма веб-интерфейс не нужен. Из корня проекта запустите
интерактивный чат:

```powershell
python -m agent_core.cli
```

Перед запуском должны быть установлены зависимости из `.[api,langgraph]` и
настроен выбранный провайдер в `.env`. В терминале отправляйте обычные сообщения
одно за другим: состояние поездки сохраняется в процессе, поэтому можно менять
условия следующими репликами. Команды `/state`, `/reset`, `/help` и `/quit`
показываются по `/help`. CLI не печатает весь JSON для frontend.

Краткая сводка показывает направления, варианты отелей и транспорта,
программный итог корзины, соответствие бюджету, допущения и незакрытые риски.
В клиентском сообщении CLI не добавляется техническая оговорка о синтетическом
каталоге; при этом агент не должен утверждать, что наличие или бронирование
подтверждено поставщиком. Проверяйте сценарии по таким критериям:

1. Запрос без направления предлагает направления; с городом — ищет отель и
   транспорт.
2. Указанные ограничения и бюджет отражаются в найденных вариантах и рисках;
   неназванные условия не должны появляться как требования.
3. Итоговая цена совпадает с программным расчётом Data; при превышении бюджета
   это явно указано, а автоматическая замена не должна скрывать конфликт.
4. В допущениях видны подставленные даты/город отправления; их можно исправить
   следующим сообщением, не повторяя остальные параметры.
5. Неразрешённые стыковки и обязательные ограничения показываются как проблемы,
   а не выдаются за проверенный план.
6. Агент сообщает только подтверждённые поля и не выдаёт расчёт за подтверждённое
   наличие или бронирование.

Чтобы проверить точные Evidence, коды причин и пошаговый trace, используйте
JSON-состояние API (`POST /chat`) либо тесты; терминальная сводка специально
остаётся компактной. Тесты не требуют credentials или реального вызова модели:

```powershell
python -m pytest -q
```
